# 手册复盘与项目经验库 设计稿

日期：2026-10-24。路径：Architectural。状态：已批准（2026-10-24）。

## Goal
每份手册收尾时，先复盘再标记完成。经验经反证后写进项目仓库 `docs/lessons/` 下的单独文件；任务文档在分支上删掉后，经验依然留存。Claude 和 Codex 在下一次设计、拆任务时都能读到并引用这些经验；被引用的经验在之后的复盘里继续接受检验，证明有害就删除。

## Non-goals
- 不在 miniplan 里实现任务文档的分支生命周期（建特性分支、合并前删稿、检查主分支只剩说明文件），这些由各项目自己的规则负责
- 不记录流程类经验
- 收尾时不自动固化，不写测试、lint 规则、钩子，也不改项目的 AGENTS.md
- 不改调度脚本的返回值，不改账本行语法
- 不做相似度检索
- 不迁移各项目本机记忆里已有的经验
- 不改预算口径，不改 lint 的预算计算
- 不发版：其他项目要等改版本号、运行 build.sh、推送之后才拿到这套机制，发版另做

## Decisions
D1: 经验怎么存 — 选 单独文件，放在 docs/ 下的单独目录 — 因为用户选择
D2: 入库前是否反证 — 选 派 critic 反证，推不翻才入库 — 因为用户选择，要确保经验真的有效
D3: 流程类经验 — 选 不记录，由人阅读后判断，自己用其他方式改进流程 — 因为用户选择：绝大多数流程并不通用
D4: 条数上限 — 选 暂定 30 条 — 因为用户选择
D5: 可固化的经验怎么处理 — 选 只在汇报里建议，由用户另起任务实施，实施后删掉该条 — 因为用户选择
D6: 引用反馈 — 选 加：设计稿引用过的经验在复盘里也打一行判定，判有害就删，判定记录累积在条目里 — 因为用户选择
D7: Codex 侧 — 选 复盘写在两侧共用的段落，改完运行 build.sh 重新生成 Codex 与 Qwen 副本 — 因为用户选择
D8: 流程类观察 — 选 只写进手册的复盘一节和收尾汇报，不进任何长期文件 — 因为用户选择
D9: 目录与文件形式 — 选 `docs/lessons/`，每条经验一个文件；不提交索引，由 `miniplan.py lessons` 当场列出 — delegated：删除、合并都只动一个文件，上限直接按文件数算；提交的索引在并行分支合并时必然冲突（反证中7）
D10: 谁写复盘 — 选 主线程写判定行和候选经验，critic 把判定行当作待推翻的主张，逐行用原始日志和改动核对 — delegated：主线程手里有整次运行的上下文和账本；critic 要推翻主张就得读到主张，独立性靠「每行都用原始材料核对」来保证；不另派复盘代理，省一次派发
D11: 判定词与有效的标准 — 选 有效、有害、无可见效果、无法归因、用户纠正。「有效」必须同时满足：同一条验收命令修复前失败（摘录失败行）、修复后通过；修复只针对一处原因；没有靠重试通过。改坏了判有害。用户在运行中明确纠正的做法判用户纠正。其余情况拿不准一律判无法归因 — delegated：Harness² 的有效、无法归因建立在多个候选的对照上（prompts.py:1110-1130）；miniplan 每次修复只有一条轨迹，确定性测试在单一改动前后的失败到通过，就是它所说的「能隔离单个部件的执行」；用户纠正是用户直接给的依据，不需要执行对照（反证高1）
D12: 什么时候派反证 — 选 只在入库时派：新增条目、合并条目。追加引用记录、判有害后删除、满额淘汰、修复失效路径由主线程做，写进复盘一节和汇报 — delegated：D2 管的是入库；引用记录是观察，不是经验；删除错了的代价小于每份手册多派一次（反证中8）
D13: 反证这次派发怎么计数 — 选 不计入手册的 `预算`，由每次请求的派发上限管；到上限就顺延到下一次运行 — delegated：`预算` 是调度脚本的上限（run-manual.js:13,378），主线程收尾时派的 critic 走 agent-guard 的按请求计数（agent-guard.sh:98-105）；计进 `预算` 反而会给调度脚本多留一次修复余量
D14: 满 30 条时 — 选 新条目入库前，主线程先淘汰一条：作用对象路径全部失效的优先，其次是最近一次被引用最早的（没被引用过的按来源日期）；淘汰写进复盘和汇报 — delegated：「从没判过有效」几乎人人满足，会退化成按时间排；按最近使用淘汰更可分辨（反证中8）
D15: 证据保存方式 — 选 支撑经验的判定行写进条目，失败输出的原文摘录放在反引号里；不引用账本行、日志路径或提交号 — delegated：手册会被删，日志 30 天清理（gate.py:16,84），项目压缩合并后提交号可能无法访问。Harness² 每轮从空库开始（library.py:20-22），没遇到过长期过期的问题，这里要自己处理（反证中5、来源对照）
D16: 机械检查 — 选 新增 `miniplan.py lessons` 检查经验库；`check` 在手册状态为已完成时要求复盘结论行，结论指向条目文件时还要求有一行 `Ruling: 经验反证 — <文件> — <结论>`；`check` 只在没有问题时才删运行标记 — delegated：Harness² 入库只查字段非空（library.py:43-47）；现在的 `check` 无论有没有问题都会删标记（ledger.py:250-252），Stop 钩子最多拦一次（反证高2）
D17: 运行中用户的纠正 — 选 记一条 `Ruling: 用户纠正 — <原话摘要>`；workflow 在后台运行时先记在会话里，运行返回后和返回的账本行一起写入 — delegated：复盘在收尾时做，对话可能已被压缩；后台运行期间不改集成副本（working/SKILL.md:56-57）
D18: 对照评测 — 选 跑一次，运行前征得同意并设费用上限 — delegated：维护说明要求改提示词后跑对照评测（docs/maintaining.md），这次改了 brainstorming 和 working 的文字

## Design

### 方案取舍
推荐方案：复盘全文写在手册里，随手册一起删；经验库只存可以照着执行的做法和支撑它的判定行；命令做机械检查，critic 在入库时反证，引用反馈负责事后检验。

被否方案一：经验写进项目 AGENTS.md 的一节。AGENTS.md 每次会话都会自动加载，等于让经验常驻付费；Harness² 的提示词也说常驻文字「paid for on every run」（prompts.py:329）。用户已在 D1 否决。

被否方案二：照搬 Harness²，每份手册把完整复盘（全部判定行和选择理由）存进库。复盘全文会像旧设计稿一样越积越多，短生命周期就没有意义了；下次设计只需要能照着执行的做法。

被否方案三：另派一个独立的复盘代理写判定行（对应 Harness² 另开会话）。多一次派发，而独立核对已经由入库反证承担（D10）。

被否方案四：先试跑几份手册的复盘、不建库，统计能产出多少经验再决定。用户要的是保存机制；产出率低的风险靠 D11 写明有效的标准来降低，并写进 Risks。

引用反馈和满额淘汰是这里新加的，Harness² 没有对应机制（它只在采用后提炼一次，selection.py 的 reflect_adoption 与 _distil）。

### 一、经验条目（`docs/lessons/<英文短横线名>.md`）
模板放在 working 的 references 里：

```
# <情境短句>

情境：<问题的形态，换一件事也能用上；不写这次的具体事实>
做法：<针对本仓库代码、测试、命令、接口或数据的操作，能照着做、能检查；可以点明在设计、拆任务或写验收命令时用>
作用对象：`<本仓库路径>`，`<路径>`
证据：
- 有效：<改动> → <差异>，失败行 `<原文摘录>`（<任务标题>，<日期>）
- 用户纠正：<原话摘要>（<日期>）
置信度：高 | 中 | 低，<理由>
来源：<手册主题>，<日期>
引用记录：
- 无
```

- 粒度照 Harness²（prompts.py:1136-1141）：太泛的不收，如「要仔细」；太窄、再也用不上的不收，如「某日某接口返回 409」
- 流程类的标准：做法换到无关仓库也照样成立，就属于流程类，不收（D3）。比如「门禁先比对测试原文」属于流程类；「这个仓库的真库测试在验收命令里要分段跑」属于项目经验
- 作用对象至少写一个本仓库里存在的路径
- 证据每行以五个判定词之一开头，至少一行是有效、有害或用户纠正；只靠无法归因或无可见效果撑着的不成经验（prompts.py:1143-1145）
- 引用记录每行写 `- YYYY-MM-DD <手册主题>：<判定>，<一句观察>`，没有时写 `- 无`
- 条目里不写任务编号、决策编号、章节号，用任务标题代替；不链接 `docs/miniplan/`

### 二、`miniplan.py lessons`
在项目根目录运行，读 `docs/lessons/`。目录不存在时打印「无经验库」，退出码 0。否则先每条输出一行 `<文件>：<情境>`，供设计阶段读取；再逐条检查，有问题就输出 `<文件>:<行>: <代码> <说明>`，退出码 1：
- `E_FIELD`：缺字段或字段顺序不对
- `E_CAP`：条目超过 30 条
- `E_EVIDENCE`：证据行不以判定词开头，或者没有一行是有效、有害或用户纠正
- `E_PATH`：作用对象里的路径不存在
- `E_MARKER`：反引号以外的文字里出现 `T<数字>`、`D<数字>`、`A<数字>`、`附录 <字母>`、`第 <数字> 轮` 这类过程标记
- `E_LINK`：提到 `docs/miniplan/`

实现放新模块 `claude/bin/mp/lessons.py`，在 `miniplan.py` 的 COMMANDS 和 build_parser 里登记（miniplan.py:7-61）。

### 三、复盘（working 新增共用一节，放在设为已完成之前）
写在 host 标记之外，Claude、Codex、Qwen 三份都会带上。时机是最终全量门禁通过之后。

1. 收集材料
   - `## Progress` 里的 repair、failed、Ruling 行
   - 账本行里给出的门禁日志
   - 修复提交的改动
   - 设计稿的 `## 引用经验`
2. 在手册末尾写 `## 复盘`
   - 判定行：每次修复、每个失败任务、每条裁定和用户纠正、每条被引用的经验各一行，格式为 `<对象> | <改动或做法> | <观察到的差异与出处> | <判定>`，判定按 D11
   - 候选经验：最多一条；没有就写「经验：无」
   - 流程观察：只列在这里和汇报里（D8）
   - 可固化建议：只列出，不实施（D5）
3. 有候选经验，或者要合并条目时，派一个 critic，契约见 working 的 references 里新增的 lesson-falsify.md
   - 必读清单：候选条目和它依据的判定行、这些判定行引用的日志、修复提交的改动、`miniplan.py lessons` 的输出、可能重复的已有条目、作用对象路径
   - 反证目标：每行判定是否被原始日志和改动支撑、是否应判无法归因；是否属于流程类；粒度太泛还是太窄；是否和已有条目重复；有没有过程标记
   - 主线程逐条裁决，写成复盘一节里的表格；被采纳的反对意见让候选失去支撑时，改为「经验：无」
   - 派发已到上限就停在这一步，在汇报里说明，下一次运行再派（D13）
   - 反证后在账本记一行 `Ruling: 经验反证 — <文件> — <入库 | 不入库，原因>`
4. 写条目，追加引用记录，处理判为有害的条目、满额淘汰（D14）和失效路径，然后运行 `miniplan.py lessons`
   - 退出码为 0 才提交，提交只动 `docs/lessons/` 和手册，提交信息写经验本身
   - 项目有检查 docs/ 的测试时，提交后跑一次项目的选测命令
5. 复盘一节最后一行写 `经验：docs/lessons/<文件>.md` 或 `经验：无`
6. 把状态设为已完成，运行 `miniplan.py check`

### 四、`check` 的改动
- 手册状态以已完成开头时，要求有 `## 复盘` 一节，且其中有一行 `经验：无` 或 `经验：docs/lessons/<文件>.md`，文件要存在；指向文件时，`## Progress` 里还要有一行提到该文件的 `Ruling: 经验反证`。缺任何一项都报 `C_NO_RETRO`，退出码 1（ledger.py:233-252）
- 运行标记只在没有问题时删除。卡住时仍可用 `miniplan.py release` 手动删除
- 能覆盖到哪里：
  - Claude 的 workflow 模式：Stop 钩子会持续拦截收尾，直到问题修好（run-guard.sh:22-36）
  - 提示词模式和 Codex 脚本模式：没有运行标记，Codex 也没有 Stop 钩子，只靠收尾步骤里显式运行 `check`
  - 「经过反证」这一条靠账本里的自报行检查；要跳过它，只能主动写假记录

### 五、读取与引用

## Risks
- 产出率可能很低：多数手册会是「经验：无」，经验库要很久才能积累起来；这是宁缺毋滥的代价
- 反证代理和写复盘的主线程是同类模型，「推不翻」不等于真的有效；有效性要靠引用反馈慢慢积累，前期样本少
- 主线程既写设计稿又给引用的经验打判定，过度约束这类静默的害处测不出来
- 「经过反证」是自报的记录，只能防止忘记，防不了造假
- 设计阶段会不会去读经验库，只靠技能里的一句步骤和模板里的「引用经验」一节，没有机械保证
- 并行分支各自新增条目，合并后可能超过 30 条，要到下一次复盘的检查才会发现
- 本仓库的路径改名后，下一次复盘要先处理失效条目，收尾因此变长
- 错了的代价：错误经验在下一次设计里被引用，把设计带偏；判为有害后才会删除
