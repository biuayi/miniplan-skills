# 借鉴 Harness² 改进门禁与契约 设计稿

日期：2026-10-23。路径：Architectural。状态：已批准（2026-10-23）。

## Goal
门禁能发现被改弱的测试；测试的完整输出留在可追溯的日志文件里，门禁结论和账本指向它；修复与交接的契约要求结论指向原始证据；改提示词后用一条命令完成改前、改后的对照评测，只把多次运行里明显的差异当退化。

## Non-goals
- 不做手册复盘与经验沉淀，只记一条待办
- 不动预算的计算、审批与放宽方式，另起一份设计
- 不运行 build.sh，不改 codex/、qwen/、dist/
- 不引入多候选并行、盲选、通用与领域两路编辑
- 不改门禁返回结构，不让门禁自己写文件
- 不改评测用例与评分器本身
- 不改预算口径，不加「实际派发数等于预期」断言
- 修复失败后不退回起点，失败任务的工作树照旧保留

## Decisions
D1: 落地哪些借鉴项 — 选 门禁查测试改弱、测试输出落文件、根因引用失败输出、契约事实标出处、一致只算旁证、会话注入长度上限、对照评测复测脚本；手册复盘记为待办 — 因为用户选择
D2: 改动范围 — 选 只改 Claude 版源文件 — 因为用户选择
D3: 待办记在哪 — 选 新建独立待办文件 `docs/todo.md` — 因为用户选择
D4: 完整证据由谁写、写在哪 — 选 测试闸门加可选参数 `--log`：子进程的标准输出与标准错误直接重定向到仓库 Git 元数据目录下 `miniplan/test-logs/` 的日志文件（不经管道），开始前与结束后各在 stderr 打印一次绝对路径，结束后把末尾 40 行打到 stdout；不加 `--log` 时行为完全不变；只清理 30 天前的日志 — delegated：门禁角色没有写文件的工具，门禁手写文件还会被测试闸门钩子拦下，Codex 会把新加的返回字段当必填（一轮高1–3）；边显示边写的管道方案会被后台子进程挂住、改变输出流走向、写日志出错时改掉退出码（二轮高1–3），改成可选的直接重定向就没有这些问题；位置与 Codex 运行器的存放目录同在 Git 元数据下
D5: 复测脚本怎样判退化 — 选 只看计分的评分项（`scored` 为真），按用例、评分项算两边有效运行里的通过率，基线比改后高 0.5 及以上记退化，反向记改善，其余有差异记波动，相同记一致；出错的运行不计入，任一边有效运行少于 2 次记「不足」；任一边结果不完整（触发费用上限）时拒绝对照 — delegated：评测默认每个用例跑 3 次，相当于差 2 次才算；两边有效次数不等时比率才公平（一轮中5、二轮中8）
D6: 会话注入长度上限 — 选 把插件根路径还原为 `${CLAUDE_PLUGIN_ROOT}` 后计长，上限为本次改后长度向上取整到 512 字节的倍数 — delegated：目的是防止精简后再慢慢涨回去，不是宿主限制；与安装路径无关（反证低10）
D7: 复测脚本放哪 — 选 `tests/eval_compare.py` — delegated：tests/ 不进任何包；`tests/run.sh` 只收 `test_*.py`
D8: 本次改动是否跑一次真实评测 — 选 跑，用复测脚本对 claude/ 跑，运行前征得同意并设费用上限 — delegated：验证脚本端到端可用，也检查基础层加句后入口路由与批准门没有退化；会计入套餐额度
D9: 复测脚本默认基线 — 选 在特性分支上取它与本地 main 的分叉点；当前就在 main 上或没有 main 分支时要求显式给 `--base`；两边插件目录内容相同时报错退出并说明插件没有改动 — delegated：按规则验证通过就提交，默认取 HEAD 会自己比自己（一轮中4、二轮中8）
D10: 对照里出现退化怎么办 — 选 只对出现退化的用例，两边各加跑一次、每边 6 次（`--case`、`--runs 6`），仍是退化才算退化 — delegated：每项 3 次时随机误报不可忽略，Harness² 也是靠重复执行区分改动效果与随机波动（二轮中8）

## Design

### 方案取舍

完整证据落文件：推荐由测试闸门落盘。被否方案一是让门禁写证据文件，门禁没有写工具，写入命令还会被测试闸门钩子拦下；方案二是每个门禁后派 runner 写文件，每次门禁多一次派发，占预算；方案三是主线程在运行结束后写，完整证据要先经过主对话。

复测脚本：推荐放在 tests/ 下的维护脚本，包装内置 `claude plugin eval`。被否方案一是做成 `miniplan.py` 子命令，会随插件发给所有用户，而这只是维护者工具；方案二是保持维护说明里的手工三步，每次都要手动对比 JSON。

### 一、门禁查测试改弱
这条借的是 Harness² 的思路「被评判的一方不能碰评判依据」（其泄漏闸门的延伸），不是它的原有机制。
- 只对有 builder 的任务加：调度脚本的门禁提示在任务有 builder 时多一段——CHECK 里给了测试代码时，先比对工作树里的测试与 CHECK 原文；再看本任务分支相对集成分支的改动里的测试文件，删除或放宽已有断言、新增跳过或只跑部分用例的标记，判 fail，并在 findings 里原样引用被删或被放宽的那一行。例外：契约的 GOAL 或 ACCEPTANCE 明确要求删除或替换这些测试。修复后的重新过门禁检查的是同一段 diff，所以修复 builder 改弱测试同样会被发现。
- 两种宿主共用这段提示；无 builder 的任务不加。
- working 提示模式的门禁规则同步一句。

### 二、测试输出落文件
- `miniplan.py test --log -- <命令>`：日志目录 = 按当前目录解析成绝对路径的 `git rev-parse --git-common-dir` 加 `/miniplan/test-logs`，环境变量 `MINIPLAN_TEST_LOG_DIR` 可覆盖（测试用它，不碰真实仓库）；文件名 `<UTC 时间 YYYYMMDDTHHMMSSZ>-<pid>.log`。
  - 子进程的标准输出与标准错误都直接指向该文件，不经管道；开始前在 stderr 打印 `miniplan test: 完整输出 <绝对路径>`，结束后把日志末尾 40 行写到 stdout，再在 stderr 打印同一行。
  - 退出码等于子进程退出码；信号转发、内存上限、槽位行为不变；嵌套调用照样只占一个槽位。
  - 目录建不了、文件开不了（不在 Git 仓库里、只读）时在 stderr 说明，退回不加 `--log` 的行为；清理 30 天前的日志，出错一律忽略；打印末尾时管道已关也忽略。
  - 不加 `--log` 时行为与现在完全一致。
- 调度脚本的门禁提示（只在非 Codex 宿主、已有测试闸门规则处加）：跑 CHECK 时用 `test --log`，evidence 里原样带上 `miniplan test: 完整输出` 那一行。
- 调度脚本在压缩证据之前，按「该前缀 + 以 `/miniplan/test-logs/<时间>-<pid>.log` 结尾的绝对路径」严格匹配，多个取最后一个，不合形状就不取；取到的路径附在账本完成行与失败行末尾，并随门禁问题进入修复提示。
- Codex 宿主不走测试闸门，行为不变；完整输出已由 Codex 运行器保存。
- working 提示模式：门禁规则同步一句，账本行的证据指针写日志路径。

### 三、根因引用失败输出
- 调度脚本的修复提示：根因假设之外，要求原样引用它所依据的失败输出那一行——门禁问题里带日志路径时从日志里摘，没有时引用门禁 findings 的原句；只改与门禁问题相关的代码，门禁没报问题的部分不动。
- working 的修复规则同步。

### 四、契约事实标出处
- 基础层 Task Contract 的 CONTEXT 说明改为：只放相关事实，每条附出处（文件:行或得出它的命令），没有出处的标为假设。
- plans 的 AGENTS and PROMPT 一节同步一句。

### 五、一致只算旁证
- 基础层 Compact Result（receive）加：几个只读子代理（scout、critic、reviewer 等）的结论一致只算旁证，它们是同一类模型，常读同一批材料；结论矛盾时读原始证据，不投票；写进设计或最终汇报的关键事实，主线程抽查原文。

### 六、会话注入长度上限
- `tests/test_skill_text.py` 加一例：执行 SessionStart 注入命令，把输出里的插件根路径还原为 `${CLAUDE_PLUGIN_ROOT}` 后按 UTF-8 字节计长，不超过 D6 定的上限。

### 七、对照评测复测脚本
- `python3 -I tests/eval_compare.py <插件目录> [--base <提交>] [--runs N] [-j N] --max-cost-usd X [--out <目录>] [-- <追加给评测命令的参数>]`
- 默认基线按 D9 取；在临时目录里用 `git archive` 取出基线版本的插件目录，把当前 evals 复制进去，两边用同一套用例；把当前工作区的插件目录复制一份，运行中改文件不影响结果；两边插件目录内容相同时报错退出。
- 两边依次执行评测命令，默认参数与维护说明一致：`--ablation none --model opus --allow-tools Write Edit --scaffold --trust-plugin --no-publish --threshold 0 --json <文件> --output-dir <目录> --max-cost-usd <X>`；`--` 之后的参数只追加。开跑前打印将要运行的总次数（用例数 × 每用例次数 × 2）。
- 读两份结果，按 D5 输出每个用例、评分项的「基线通过/有效次数、改后通过/有效次数、标记」，同时写一份汇总 JSON；有退化时退出码 1，拒绝对照或「不足」时退出码 2；有退化时末尾打印按 D10 复核的命令（`--case <用例> --runs 6`）。
- 判定逻辑放在可导入的函数里，`tests/test_eval_compare.py` 用造好的结果 JSON 测试，不调模型。
- `docs/maintaining.md` 对照评测一节改为用该脚本，写明评测默认每个用例跑 3 次。

## Acceptance
A1: 有 builder 的任务的门禁提示含「测试被改弱判 fail、引用被删的那一行、契约明确要求时例外」，无 builder 的任务不含；working 提示模式同步；流程仿真测试断言两种情况
A2: `tests/test_gate.py`（用 `MINIPLAN_TEST_LOG_DIR` 指向临时目录）覆盖：`--log` 写出含标准输出与标准错误的日志、开始与结束都打印同一绝对路径、stdout 是日志末尾、退出码与原命令一致；被测命令留下后台子进程时包装进程照常返回；日志目录不可写时退回原行为且退出码不变；30 天前的日志被清理；不加 `--log` 时输出与现在相同。流程仿真测试断言：门禁 evidence 含合规路径时完成行与失败行末尾附该路径、修复提示保留该路径，不合规或缺失时行与现在相同；Codex 宿主的门禁提示不含 `--log` 要求
A3: 修复提示要求原样引用失败输出的一行（有日志从日志摘，否则引用 findings 原句）、只改与门禁问题相关的代码；working 修复规则同步；流程仿真测试断言
A4: 基础层 CONTEXT 说明含「出处」与「假设」要求；plans 同步；grep 断言
A5: 基础层 Compact Result（receive）含「一致只算旁证、矛盾读原始证据不投票、关键事实抽查原文」；grep 断言
A6: 会话注入长度测试存在且通过，按 D6 计长与取上限
A7: `tests/eval_compare.py --help` 正常；`tests/test_eval_compare.py` 覆盖退化、改善、波动、一致、不足五种标记，按通过率比较、只计 `scored` 评分项、出错运行不计入，结果不完整时拒绝对照，两边插件目录相同时报错，在 main 上未给 `--base` 时报错，以及退出码 0、1、2；维护说明改用该脚本

A10: 用复测脚本对 claude/ 跑一次（基线为本次改动前的提交）；出现退化时按 D10 复核，复核后没有退化

## Risks
- `--log` 下门禁在 Bash 结果里只看到末尾 40 行，要看更多需读日志文件；输出量大的测试会占用 Git 元数据目录空间，只按 30 天清理，不设大小上限
- 账本里的日志路径是本机路径，换机或超过 30 天被清理后失效；它只用于本机追查
- 门禁可能漏带或转述错日志路径：严格匹配不合形状的不取，账本行退回原样；形状合规但内容是编造的，脚本无法核对，靠主线程抽查
- Bash 超时被杀时没有结束行，但开始前已打印路径，日志里留有已产生的输出
- 「测试被改弱」靠门禁判断，没有程序化比对；手册没给测试代码的任务只能看 diff
- 下次运行 build.sh 时，Qwen 会拿到同样的门禁与修复提示；Qwen 也走测试闸门，日志行为一致，Codex 分支不受影响
- 基础层每会话注入，加两句会让所有会话多读几百字节
- 复测脚本依赖评测结果 JSON 的字段（`cases[].arms.with[].graders[].passed`、`error`、`runsPerCase`、`partial`），CLI 升级改字段时会失效；单元测试按当前结构造夹具
- 评分器多为「不得调用某工具」的否定式断言，复测只能看到这些断言的变化，看不到路由行为的细微差异
- 两边顺序运行，期间限流可能让后一边出错更多；出错运行不计入、有效次数不足记「不足」来缓解
- A10 消耗额度；评测用例只覆盖入口路由、批准门与简单任务，不覆盖工作流调度，门禁相关改动只靠流程仿真测试
